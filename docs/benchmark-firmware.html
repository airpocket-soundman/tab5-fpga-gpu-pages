GPU LAB 評価ファーム

実装範囲

Tab5単体で動くESP-IDF / C++17ファーム。Espressif公式Tab5 BSP 1.3.2とLVGL 9を使用する。

描画は独自CPUラスタライザ、UIとタッチはLVGL。横向き1280×720のダークUIに、

640×360 RGB565の等倍映像とCPU/FPGA比較グラフを表示する。

3D変換はまず浮動小数点で実装。FPGAで固定小数点化する際は精度条件をそろえる。

この段階では汎用3Dモデル読み込み、テクスチャ、GPU通信、ハードウェア高速化は未実装。

ビルド・書き込み

ESP-IDF 5.4以上・6.0未満のESP32-P4対応環境を有効にし、リポジトリのルートで実行する。

初回はComponent ManagerがBSPなどを取得する。解決された依存版はdependencies.lockに保存される。


idf.py set-target esp32p4

idf.py build

idf.py -p COM番号 flash monitor

USB書き込み端子・COM番号は実機に合わせる。PSRAMが必要。

既定は16MB Flash、ESP32-P4 Rev 1.x（Rev <3）向け。Rev 3.xの機体ではmenuconfigで

ESP32P4_SELECTS_REV_LESS_V3を無効にして最小リビジョンを選び直す。

既存sdkconfigがある場合はdefaultsの変更が自動反映されないため、menuconfigで設定を確認する。

アプリ領域は4MB、OTAは未対応。

BSPが対応するLCD種類を利用する。横向き回転・タッチ座標・RGB565色順は実機で確認する。

CPU描画は単一タスク、PSRAM上のRGB565バッファ2面と16bit深度1面（計約1.38MB）を使用する。

LVGLとLCDドライバが使うメモリは別途必要。表示同期によるティアリング抑制は未検証。

LVGLの動的メモリはESP-IDFの標準malloc/freeを使用し、固定64KBの専用領域に制限しない。

流れの描画では残像バッファ1面と粒子配列を追加で保持する。USB画像取得時にも一時メモリが必要。

操作

  • SCENE：8シーンを巡回。
  • LOAD：3段階の負荷を巡回。グラフもその負荷の結果へ切り替わる。
  • CPU / GPU：バックエンド切替。現段階のFPGAは未実装通知を出しCPUを維持する。
  • PLAY / PAUSE：アニメーション停止・再開。測定中なら測定をキャンセル。
  • BENCH：選択シーン・負荷を測定。
  • RUN SUITE：選択バックエンドで8シーン×3負荷を順次測定。

シーン・負荷・モードの変更は進行中の測定をキャンセルする。測定済みの結果は保持。

同一条件を再測定すると上書き。結果はRAMのみで、再起動すると消える。

負荷の高いフラクタルは1フレーム完了まで操作の反映に時間がかかる。

測定の定義

BENCHとSUITEはフレーム番号を0へ戻し、24フレームをウォームアップ、続く120フレームを採用する。

アニメーションは時刻でなくフレーム番号に依存し、バックエンド間で同じ計算対象にする。

フレーム上限を設けずに実行。各フレームに1 RTOS tickの待機を入れ、タスクの実行機会を確保する。

  • render_mean_ms：クリア・座標変換・描画を含むバックエンド呼び出し時間の平均。
  • render_p95_ms：描画時間を昇順にしたnearest-rank 95パーセンタイル。
  • pipeline_mean_ms：描画開始からLVGL更新処理、ロック待ち、1 tick待機を含む時間の平均。
  • frame_fps：1000 / pipeline_mean_ms。実液晶の走査FPSではない。

ライブ値は直近フレームの参考値。測定グラフは120フレームの集計値。

グラフは同じ負荷・640×360・RGB565の結果を共通スケールで表示する。

GPU結果が無い間は欠測「--」。0 FPSや推定値として描かない。

グラフの倍率はGPU frame_fps / CPU frame_fps。

UIの数値・進捗変更に伴う描画負荷も存在するため、純粋なラスタライザ性能にはrender_mean_msを使う。

CPU使用率、LCD走査FPS、転送帯域、複数回測定のばらつきはまだ集計しない。

シリアルに以下の形式で出力する。行頭がBENCH,の行を抽出してCSVとして保存できる。

USBはJSON API専用。以下のログはUART側へ出力し、USBからはresultsコマンドで取得する。


BENCH_HEADER,schema,mode,scene,load,width,height,frames,render_mean_ms,render_p95_ms,pipeline_mean_ms,frame_fps

BENCH,1,CPU,0,0,640,360,120,...

sceneは上の表の順で0〜7、loadは0〜2。ヘッダ先頭列をtypeとして読み替える。

ボード・クロック・IDF版・コミット・LCD設定を測定ログと一緒に記録すること。

FPGA接続時

main/lab.hppのBackendを共通契約とする。Fpga::availableはシーン別の実装有無・接続状態を返す。

renderは同じRequestを受け取り、Target.colorへ完成フレームを返す同期API。

コマンド送信・FPGA完了待ち・PARLIO受信までをrender時間に含め、同じ表示経路へ渡す。

未対応シーンや通信失敗ではfalseを返し、CPUへの暗黙フォールバックは行わない。

現行のFpgaは常に未対応を返し、GPIOへアクセスしない。

将来のコマンド仕様ではフレーム番号、シーン、負荷、解像度、数値精度、プロトコル版を固定する。

CPUとFPGAの画像・深度・フラクタル反復を照合してから速度比較を有効にする。

転送時間・FPGA内部時間は今後分離する。現段階のC++ APIはオンワイヤのプロトコルではない。

ホスト検証

C++17コンパイラで以下を実行する（buildフォルダを事前作成）。


c++ -std=c++17 -O2 -Wall -Wextra -Werror -I main main/lab.cpp tests/renderer_test.cpp -o build/renderer_test

build/renderer_test

全シーン・全負荷、同条件の再現性、アニメーション変化、Zバッファ更新、バッファ前後のガード、

集計・p95・無効入力・GPU未対応を検査。確認用画像をbuild/scene_0.ppm〜scene_7.ppmへ出力する。

ホスト検証はESP-IDFビルドと実機動作の代わりにはならない。
