開発資料の公開と更新

公開構成

開発リポジトリ airpocket-soundman/tab5-fpga-gpu と、公開専用リポジトリ

airpocket-soundman/tab5-fpga-gpu-pages を分離する。

開発側で生成・レビューした build/site/ のHTML成果物だけ を公開側へコピーする。

公開側はmainブランチのルートをGitHub Pagesの配信元とする構成。

開発側のprivateリポジトリでは、現在のアカウントプランによるPages有効化がHTTP 422で拒否されたため、

公開専用リポジトリを用いる。元リポジトリのvisibilityは変更しない。

公開専用リポジトリの作成、Pages有効化、公開URLでの取得確認は、それぞれ別途結果を確認する。

この手順書やworkflowの追加だけでは公開成功を意味しない。

更新手順

  • 元リポジトリの仕様・ロードマップ・評価資料を更新する。実装済み、実測、計画、未検証を区別する。
  • リポジトリのルートで python tools/build_site.py を実行する。Python標準ライブラリだけで生成する。
  • build/site/index.html をローカルで開き、文面・リンク・表示・公開対象ファイルを確認する。
  • 公開専用リポジトリの作業ツリーに build/site/ の中身だけを反映する。元リポジトリ全体や.git/はコピーしない。
  • 公開側へコミット・pushする。mainルートを配信元とするPages更新の完了を待つ。
  • GitHubが返すPages URLを開き、更新した内容を確認する。失敗時はデプロイ結果を確認し、公開済みと報告しない。

削除された古い成果物が公開側に残らないことも確認する。公開側での削除は、公開専用作業ツリーと

管理対象ファイルを確認してから行う。秘密情報や他用途のファイルが混ざったディレクトリを一括同期しない。

CIの役割

workflow（開発リポジトリ内） はmainへのpushまたは手動実行で、

python tools/build_site.py を実行し、build/site/ のみを

public-documentation-site というActions成果物として7日間保存する。

生成失敗・成果物なしは失敗として扱う。

CIは元リポジトリの読み取り権限 contents: read だけを使う。

公開リポジトリへの自動pushやPagesデプロイは行わず、公開用tokenやsecretを必要としない。

公開側への反映は上記のレビュー済み成果物を使う手順で行う。

公開対象と秘密情報

privateリポジトリから生成したGitHub Pagesでも、サイトは公開アクセス可能になりうる。

今回の公開専用リポジトリは公開を目的とするため、ソース側がprivateであることを

生成ページの秘密保持と取り違えない。

GitHub公式のPages公開条件

を確認する。

token、認証情報、個人情報、秘密鍵、非公開URL、開発環境のsecret、公開許諾のないモデルやデータを

HTML・画像・ログ・Actions成果物に含めない。build/全体、ファームbin、モデルファイル、

端末ログをそのまま公開しない。実測結果は公開範囲を確認し、比較条件と未測定項目を明記する。

この公開・生成workflowにはTab5、USB、COM、FPGAプログラマへの操作は含めない。

Tab5実機へのアクセス・書込み停止は継続する。
